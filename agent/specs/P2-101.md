# P2-101 — Passer à Melos 7 et plus : ce que la migration implique

Tâche de la file (statut `humain`). Document de conception seulement : aucune
modification de configuration. Il explique pourquoi les PR Dependabot #18
(Melos 8.9.0) et #243 (Melos 8.10.0) échouent et ce qu'il faudrait décider
pour les rendre fusionnables.

## 1. Pourquoi les PR Dependabot échouent

La CI de #18 s'arrête à `melos run format` avec `NoScriptException: This
workspace has no scripts defined in its 'pubspec.yaml' file`. Melos 7 et plus
ne lit plus `melos.yaml` : la configuration doit se trouver sous la clé
`melos:` du `pubspec.yaml` racine. Le saut 6 → 8 n'est donc pas une simple
mise à jour de version.

La CI de `main`, elle, passe : elle installe Melos en global avec
`dart pub global activate melos` (dernière version), mais l'exécutable global
s'efface derrière la version locale du workspace, fixée par `melos: ^6.1.0`
dans le `pubspec.yaml` racine.

## 2. Ce que demande la migration (documentation de Melos)

D'après le guide de migration 6 → 7 de Melos (dépôt `invertase/melos`,
`docs/guides/migrations.mdx`, lu le 2 novembre 2026) :

1. `melos clean`, pour retirer les `pubspec_overrides.yaml` générés.
2. Ajouter `resolution: workspace` au `pubspec.yaml` de **chaque** paquet.
3. Lister les paquets sous une clé `workspace:` du `pubspec.yaml` racine.
4. Déplacer le contenu de `melos.yaml` (sauf `name` et `packages`) sous la clé
   `melos:` du `pubspec.yaml` racine, puis supprimer `melos.yaml`.
5. **Dart SDK 3.9.0 ou plus**, d'après ce même guide, pour que les pub
   workspaces fonctionnent de façon fiable.

## 3. La vraie décision : relever le SDK minimal de 3.3 à 3.9

Le point 5 n'est pas technique, c'est un choix de produit :

- `CLAUDE.md` et chaque `pubspec.yaml` annoncent **SDK ≥ 3.3**. Un éditeur dont
  l'application est bloquée sur un SDK entre 3.3 et 3.8 ne pourrait plus
  intégrer Écluse.
- Passer la contrainte à 3.9 change la **version de langage** des paquets. Or
  `dart format` choisit son style selon cette version : à partir de la 3.7,
  c'est le nouveau style « tall ». La migration reformaterait donc **tout le
  dépôt** en une fois, avec un gros diff sans changement de comportement.
- La CI utilise déjà le SDK stable (3.13.7 le 2 novembre 2026) : elle n'est
  pas le point bloquant.

## 4. Options

| Option | Effet | Coût |
|---|---|---|
| A. Rester sur Melos 6 | Rien ne change ; fermer #18 et #243 | Dependabot rouvrira une PR à chaque version de Melos tant qu'on ne lui dit pas d'ignorer les versions majeures (fichier `.github/dependabot.yml`, zone du mainteneur) |
| B. Migrer maintenant | Pub workspaces, Melos à jour | SDK minimal 3.9 ; reformatage complet ; à faire dans une PR isolée, sans autre changement, pour garder un historique lisible |
| C. Migrer à la phase 3 | Avec le SDK JS/TS et la distribution, quand la question du SDK minimal se posera de toute façon pour les éditeurs | Reporter la question, mais au moment où l'on parle aux éditeurs de compatibilité |

## 5. Recommandation (avis, pas décision)

**Option A maintenant, option C plus tard.** Aucune fonctionnalité de Melos 7
ou 8 n'est attendue par la file actuelle, et relever le SDK minimal est une
promesse de compatibilité retirée aux intégrateurs. La question mérite d'être
posée avec les premiers éditeurs, pas tranchée par une mise à jour d'outillage.

Concrètement, côté mainteneur :

1. Fermer #18 et #243 avec un commentaire qui renvoie à cette spec.
2. Dans `.github/dependabot.yml`, ignorer les mises à jour majeures de `melos`
   (bloc `ignore` avec `update-types: ["version-update:semver-major"]`).
3. Remplacer la ligne de `DECISIONS.md` (« #18 à tester en local avant
   fusion ») par la décision prise.

## 6. Ce que ce document ne sait pas

- Si des fonctionnalités d'analyse ou de test changent de comportement entre
  les versions de langage 3.3 et 3.9 pour ce dépôt : non mesuré.
- Le SDK réellement utilisé par les éditeurs visés.
