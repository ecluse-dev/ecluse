# P2-198 — Journal d'audit : que faire quand la version du moteur change

Type `spec` : aucune ligne de code modifiée. Rédigée le 15 novembre 2026 sur
`main` au commit `b3b6d8e`. Les décisions restent au mainteneur ; chaque
question a ses options, ses avantages, ses risques et une recommandation.

## Contexte : ce que fait le code aujourd'hui

- Une entrée porte `engine`, une chaîne « version du moteur et noms des
  détecteurs actifs » (`packages/ecluse_audit/lib/src/audit_entry.dart:140-141`).
  Pour `Ecluse.redact`, elle vaut `ecluse_redact 0.2.0 [nir,rpps,…]`
  (`packages/ecluse_redact/lib/src/ecluse.dart:180-195`, construite aux
  lignes 314-322 d'après les détecteurs réellement utilisés, supplémentaires
  compris). **La version et la liste des détecteurs sont donc dans une même
  chaîne** : un changement de détecteurs sans changement de version produit
  déjà une valeur `engine` différente.
- `engine` est validée par une forme (`audit_chain.dart:13`,
  `^[A-Za-z0-9_.,+\- \[\]]{1,200}$`) et écrite telle quelle par
  `JournalAudit._enregistrer` (`journal_audit.dart:67-89`). Quand la description
  dépasse 200 caractères, seul le nombre de détecteurs est écrit
  (`ecluse.dart:193-194`) : la liste n'est alors plus dans le journal.
- `JournalAudit` accepte une `derniere` pour reprendre une chaîne
  (`journal_audit.dart:28-34`) : une mise à jour de l'application suivie d'un
  redémarrage produit exactement le cas de la fiche, première entrée de la
  nouvelle version avec `prev` = hash de la dernière de l'ancienne.
- Le test `versionMoteur suit la version de pubspec.yaml`
  (`packages/ecluse_redact/test/journal_audit_redact_test.dart:121-126`) tient
  la constante égale au `pubspec.yaml` : la version change à chaque publication
  du paquet, y compris pour un correctif.

## Question 1 — La chaîne de version fait-elle partie de l'empreinte chaînée ?

**État actuel : oui.** `toHashableJson` inclut `'engine': engine`
(`audit_entry.dart:159-168`) ; `computeHash` hache cette forme
(`audit_entry.dart:176`) et `AuditVerifier.verify` recalcule chaque hash
(`audit_verifier.dart:61`). Modifier la valeur `engine` d'une entrée après
coup la fait signaler `invalidHash` : c'est voulu.

| Option | Avantage | Risque |
|---|---|---|
| A. Statu quo : `engine` dans le hash | Réécrire l'historique des versions est détecté ; aucun changement de schéma | Aucun, hormis la conflation version/détecteurs ci-dessous |
| B. Sortir `engine` du hash (métadonnée libre) | Corriger une version mal écrite sans casser la chaîne | **Casse la garantie** : l'historique des versions devient réécrivable sans détection. Contraire à l'objet du journal (la « version du moteur » figure parmi les mesures de sécurité du tableau AIPD de `agent/specs/P1-08-audit.md`) |
| C. Séparer `engine_version` et `detecteurs` (deux champs hachés, schéma 3) | Comparer les versions sans parser une chaîne ; un changement de détecteurs sans changement de version se lit directement | Nouvelle version de schéma : un lecteur de schéma 2 refuse les entrées de schéma 3 (`audit_entry.dart:111-113`) ; migration des tests et de l'export |

**Recommandation : A.** Garder `engine` dans le hash. La conflation n'est un
problème que pour l'export (question 3), et C ne se justifie qu'avec une
demande d'un DPO de distinguer les deux.

## Question 2 — Un journal mixte est-il valide, signalé ou refusé ?

**État actuel : valide, sans aucun signalement.** `AuditVerifier.verify` ne
regarde jamais `engine` : il contrôle le hash, `seq` et `prev`
(`audit_verifier.dart:54-87`). Deux versions dans un même journal donnent
`AuditIntact`. Aucun test de vérification ne mélange deux moteurs valides
(`audit_test.dart` n'en utilise qu'un, plus une forme invalide pour le refus ;
seul `audit_export_test.dart:88-101` en mélange deux, pour l'export).

| Option | Avantage | Risque |
|---|---|---|
| A. Valide et muet (statu quo) | Aucun travail | Un changement de moteur en cours de période passe inaperçu à la lecture du résultat de vérification |
| B. Valide **et signalé** : le résultat de vérification (ou l'export) porte le nombre de changements de `engine` et leur rang (`seq`) | Un changement est visible sans interdire la mise à jour ; pas de changement de schéma | Une ligne de plus dans l'API de sortie ; la notion de « changement » doit être définie (version seule, ou version + détecteurs) |
| C. Refusé (`AuditBroken` nouvelle nature `engineChange`) | Force à décider | **Une simple mise à jour logicielle casserait un journal par ailleurs intact** : faux positif de falsification, contraire à l'esprit d'`AuditBroken` (une rupture = intégrité, `audit_verifier.dart:3-13`) |

**Recommandation : B**, dans l'export plutôt que dans `verify` (la
vérification dit l'intégrité, pas l'histoire). `verify` reste inchangé.

## Question 3 — Que dit l'export AIPD d'un changement de version en cours de période ?

**État actuel :** `AuditExporter.agrege` rassemble les valeurs distinctes de
`engine` dans un ensemble (`audit_export.dart:164,172`), les **trie
alphabétiquement** (`:201`) et les imprime « Moteurs : a ; b » (`:109`) ou les
sort sous `moteurs` en JSON (`:74`). Constats :

1. **Pas d'ordre chronologique** : le tri est lexicographique. `ecluse_redact
   0.10.0` se classerait avant `0.2.0`. Rien ne dit quelle version a traité
   quelles opérations ni à quelle date.
2. **Pas de compte par version** : impossible de dire que 12 opérations ont
   été faites avec l'ancien moteur et 480 avec le nouveau.
3. **La liste de détecteurs gonfle l'ensemble** (une valeur par jeu de
   détecteurs, même sans changement de version).

| Option | Avantage | Risque |
|---|---|---|
| A. Statu quo (liste triée) | Aucun travail | Le lecteur d'AIPD ne voit pas qu'il y a eu un changement ni quand ; ordre trompeur |
| B. Liste **ordonnée par première apparition**, avec pour chaque valeur le rang et l'horodatage de première entrée | Montre la succession ; aucun compte supplémentaire publié | Aucun nouveau recoupement (pas de compte) ; l'horodatage suit la règle « au jour » existante (`:175-176`) |
| C. B + opérations par valeur | Répond « combien avec quel moteur » | **Recoupement (P2-26)** : un compte par moteur sous le seuil doit être masqué (« moins de 5 », `:209-210`) et peut se retrouver par soustraction du total ; il faudrait étendre la règle `nonCommunique` à cette nouvelle ventilation |

**Recommandation : B** avec, en plus, la mention explicite « le moteur a
changé N fois pendant la période » quand N ≥ 1 (donnée de B, sans compte par
version). C seulement si une demande formelle l'exige, avec sa propre
analyse de recoupement. Les mentions d'honnêteté (`mentionsAudit`,
`:137-150`) gagneraient une phrase : « un changement de version ne change pas
les garanties du journal, mais les détections avant et après ne sont pas
comparables ».

## Question 4 — Faut-il une entrée « changement de moteur » ?

**État actuel :** aucune. L'énumération `AuditOp` est fermée
(`audit_entry.dart:6-13` : `redact`, `ingest_refused`, `secrets_refused`) et
`fromJson` refuse un `op` inconnu (`:94-95`).

| Option | Avantage | Risque |
|---|---|---|
| A. Aucune entrée : le changement se lit dans `engine` de deux entrées consécutives | Pas de schéma 3 ; un lecteur de schéma 2 relit tout | Un changement sans opération (aucune entrée ensuite) n'est pas journalisé |
| B. Nouvelle opération `engine_changed` (schéma 3), écrite automatiquement par `JournalAudit` quand `moteur` diffère de `_derniere.engine` | Événement explicite, daté, dans la chaîne | (1) l'énumération grandit : un lecteur de schéma 2 **refuse** le journal (`fromJson`, `:94-95`, `:111-113`) ; (2) l'entrée compte dans `operations` et fausse le total et les seuils de faible effectif (`audit_export.dart:180-184`) tant que l'export ne l'exclut pas ; (3) `JournalAudit` écrirait **deux** entrées dans `_enregistrer`, ce qui complique la sérialisation et l'échec partiel (« un échec n'avance pas la chaîne », `journal_audit.dart:19-21`) |
| C. Déduire le marqueur à la lecture (export, question 3 B) | Même information qu'une entrée dédiée, sans les trois risques de B | Le marqueur n'est pas dans la chaîne : il n'est pas, à lui seul, une preuve |

**Recommandation : A pour le journal, C pour l'export** (question 3 B). Une
entrée `engine_changed` se justifierait si un DPO demandait un événement
explicite ; elle imposerait alors un schéma 3, l'exclusion de ce type des
totaux et une décision sur la compatibilité de lecture.

## Récapitulatif des recommandations

1. `engine` reste dans le hash (statu quo).
2. Un journal mixte reste valide ; la vérification ne change pas ; le
   signalement est fait par l'export.
3. L'export liste les moteurs **dans l'ordre de première apparition**, avec
   rang et horodatage, et signale le nombre de changements ; aucune ventilation
   par version des comptes.
4. Pas de nouvelle opération ; déduction à la lecture.

Ce qui découle de ces recommandations, si elles sont retenues : une tâche
`code` dans `ecluse_audit` (export seulement : `AuditExport.moteurs` devient
une liste ordonnée avec rang et horodatage ; mention ajoutée ; tests : un
journal à deux versions, trois changements, ordre `0.10.0` après `0.2.0`,
horodatage « au jour » sous le seuil, absence de compte par version ; `LIMITES.md`
§ 8 et `agent/specs/P2-09.md` à mettre à jour), changement de **format** de
`moteurs` dans la sortie JSON de l'export (`version` de l'export à passer de 1
à 2 : à décider).

## Ce que cette spec ne tranche pas

- La **notion de « changement »** : version seule, ou version + détecteurs. La
  valeur `engine` contenant les deux, la plus simple est la comparaison de
  chaînes entières ; le cas « description tronquée à 200 caractères » (nombre
  de détecteurs seul) y produit un changement faux quand la liste change sans
  que le nombre change. Hors périmètre ici, à mesurer avant la tâche `code`.
- L'effet d'un **retour en arrière** de version (0.2.0 → 0.1.0 → 0.2.0) : la
  recommandation B l'affiche comme deux changements.
- La valeur juridique d'une mention de version dans une AIPD (avis d'un DPO
  attendu, cf. les mentions d'honnêteté de l'export).
