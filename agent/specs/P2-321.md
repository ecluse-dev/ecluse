# P2-321 — Politique unique des avertissements « à vérifier » (spec)

Type : spec. Aucune ligne de code de production. Date : 27 novembre 2026.

Chemin mesuré par tous les chiffres ci-dessous : **`Ecluse.redact`** (ce que reçoit
le LLM), sauf mention contraire. Aucun chiffre n'est rejoué dans cette spec : chacun
est repris de `bench/ETAT.md` (« ETAT »), de `LIMITES.md` (« LIM ») ou d'une spec
du dépôt, et sa source est citée. Quand les sources ne donnent pas de chiffre, la
case dit **non mesuré** : rien n'est estimé.

Inventaire fait en lisant `packages/ecluse_redact/lib/src/ecluse.dart` (liste
`warnings` de `_redact…`, lignes ≈ 598-622 et fonctions `_avertissement*`), puis
`packages/ecluse_ingest/lib/src`, `packages/ecluse_reid/lib/src` et
`packages/ecluse_demo/lib/src`.

## 1. Tableau : type × message × seuil de bruit × corpus de référence × coût mesuré

Le « seuil de bruit retenu » est celui que les sources écrivent. Le seul seuil
écrit comme règle d'arrêt est celui de P2-310 : **plus de 5 % d'un témoin propre
en casse ordinaire**. Pour les autres avertissements, les sources ne fixent pas de
seuil : la case dit « aucun écrit ».

## 2. Règle commune proposée : « avertir ou taire »

Proposition. Les avertissements existants obéissent tous, dans les sources, à une
même idée : « une garde ne rend jamais une donnée silencieuse » (principe du
26 novembre, point 0, `DECISIONS.md` ; règle 4 de `CLAUDE.md`). La règle écrit ce que
les sources font déjà au cas par cas.

1. **Avertir** dès qu'un candidat est écarté ou laissé en clair par une garde, un
   filtre de liste, une réserve de lecture ou une limite de format, et qu'**aucune
   entité à confiance forte ne le couvre en entier** (c'est le test de P2-309 et
   P2-312, `_couvertEnEntier`). Le message donne un type, un compte et des
   positions, **jamais la valeur** (invariant déjà tenu par les n° 4 à 12).
2. **Taire seulement** ce qui est couvert (doublon d'une entité masquée) ou ce
   qu'aucun test de sonde ne reconnaît comme un identifiant possible (clé fausse
   de quatorze chiffres : « rien ne les distingue d'un nombre ordinaire », LIM
   § P2-307). Une garde qui réduit le bruit ne doit pas rendre un cas de sonde
   silencieux ; si c'est le cas, la garde est retirée (règle de P2-318).
3. **Réduire le bruit en baissant la pression, pas en taisant.** Trois niveaux :
   - **pressant** : donnée masquée à confiance faible ou secret (n° 1, 2, 3, 15) ;
   - **à vérifier** : donnée possible laissée en clair (n° 4, 6, 7, 8, 10, 11, 12) ;
   - **information** : message moins pressant, bruit connu et accepté (n° 5, 9,
     13, 14), formulation de P2-299 déjà dans ce sens.
4. **Seuil de bruit commun** : 5 % d'un témoin propre en casse ordinaire (repris de
   P2-310), appliqué au pire corpus d'un groupe (comme `bench/etat.sh` depuis
   P2-320). Dépassement : on ne retire pas l'avertissement ; on cherche une règle de
   non-signalement qui garde la sonde à 100 %, sinon l'avertissement **descend d'un
   niveau** et le dépassement est écrit dans `LIMITES.md`.
5. **Un message par type et par document**, avec le compte (déjà le cas : « Un
   document ne porte jamais plus d'un avertissement de ce type », ETAT § P2-310).
6. **Corpus de référence obligatoire** : chaque nouvel avertissement arrive avec
   sa ligne dans `bench/etat.sh` (sa sonde, ses témoins propres, son coût) ; sans
   cette ligne, pas de fusion. P2-320 met la première en place pour le n° 9.

**Exceptions** (écrites, pas déduites) :
- n° 13 et 14 : décrivent le **texte**, pas un candidat ; le bruit est par
  construction « tous les documents en minuscules ». Hors seuil de 5 %, mais ils
  restent au niveau « information ».
- n° 1 et 15 : suivent une action déjà faite (masquage d'un secret, jeton rencontré) ;
  pas de candidat écarté, pas de seuil.
- `ecluse_ingest` : refus ou signalement explicite d'un contenu **non lu** (règle 4) ;
  ces messages n'ont pas de « bruit » au sens du seuil, ils décrivent ce qui n'a pas
  été lu. Jamais en dessous de « à vérifier ».

## 3. Présentation proposée dans l'aperçu (sans code)

Proposition, à valider par le mainteneur avant toute tâche de code.

- **Regroupement par niveau**, dans l'ordre pressant, à vérifier, information.
  Aujourd'hui `warnings` est une liste plate de chaînes : un pilote verra jusqu'à
  une dizaine de lignes de même poids.
- **Un compteur par niveau** en tête de l'aperçu (« 2 à vérifier, 1 information »),
  et les messages **repliés** pour le niveau « information » (n° 5, 9, 13, 14).
- **Position cliquable** : chaque message porte déjà les cinq premières positions ;
  l'aperçu doit les surligner dans le texte (cohérent avec le mode « aperçu +
  validation en un clic » de la ROADMAP).
- **Plafond de lisibilité** : au-delà d'un nombre à fixer par une mesure (nombre
  moyen d'avertissements par document sur un corpus réaliste, **non mesuré
  aujourd'hui**), le niveau « information » est replié par défaut ; le niveau
  « pressant » ne l'est jamais.
- **Aucun avertissement ne bloque** l'envoi à lui seul (comme aujourd'hui) ;
  « pressant » demande une confirmation, c'est une décision produit pour le
  mainteneur.

## 4. Limites de cette spec

- Les chiffres des lignes 1, 14, 15 et de tout `ecluse_ingest` / `ecluse_reid` sont
  **non mesurés** : les sources lues n'en donnent pas. Une tâche de mesure est
  proposée dans le compte rendu de session (nombre moyen d'avertissements par
  document sur chaque corpus, par niveau).
- Le classement en trois niveaux est une proposition de cette spec ; aucun niveau
  n'existe dans le code.
- Le tableau ne distingue pas encore le coût « documents avertis » du bénéfice
  « identifiants couverts par l'avertissement » ; seules les lignes 4, 5, 6, 8, 9,
  11 et 12 portent les deux.
- Non rejoué : aucune mesure. Le tableau de bord n'est pas touché par cette PR.
