# P2-264 — Fuite par OCR (« O » pour 0, « l » ou « I » pour 1) sans libellé

Type : `mesure`. Aucun code de production n'est modifié. Les trois scripts
ajoutés sont des outils de banc : `bench/generate_corpus_ocr.py` (graine 42),
`bench/score_ocr.py`, `bench/ocr_proposition.py` (prototype hors `lib/`).

## Chemin mesuré

**`Ecluse.redact`** (chemin produit, vue de détection comprise), via
`run_redact_bench.dart` sur `bench/flou/corpus_ocr.jsonl` (1 600 documents,
graine 42, synthétique). Ce n'est pas le moteur seul (`run_ecluse.dart`).
Le prototype de correction, lui, est un script Python qui n'entre pas dans le
produit : ses chiffres sont une **simulation**, pas une mesure du produit.

Corpus : 5 types × 3 confusions (« O » pour 0, « l »/« I » pour 1, les deux)
× 2 présentations (avec libellé fort / sans libellé) × 40 documents = 1 200,
plus 400 documents témoins négatifs (mots et références ordinaires contenant
ces lettres, sans aucun identifiant).

## Lecture

1. Sans libellé, un identifiant lu avec des lettres d'OCR part en clair pour
   NIR, RPPS, FINESS et SIREN (≈ 98–100 %). Seul l'IBAN résiste en grande
   partie (la chaîne « FR » + longueur donne un ancrage).
2. Avec libellé fort (P2-191), le RPPS est entièrement couvert, le NIR à 77 %,
   l'IBAN à 87 %. **FINESS et SIREN ne sont pas couverts même avec libellé** :
   la relecture des lettres n'y est pas branchée (écart, à confirmer
   par le mainteneur : peut-être voulu, ces deux types sont des identifiants
   d'établissement, pas de personne).
3. La confusion « l/I pour 1 » fuit plus que « O pour 0 » pour le NIR.

## Proposition chiffrée (simulation, `bench/ocr_proposition.py`)

Règle : suite de 9 à 34 caractères de l'alphabet `[0-9OolI]` (séparateurs de
groupe tolérés), contenant **au moins une lettre d'OCR**, qui devient un
identifiant valide **une fois les lettres relues** comme des chiffres (NIR :
forme + clé mod 97 ; RPPS : 11 chiffres + Luhn ; IBAN FR : mod 97 ; FINESS /
SIREN : 9 chiffres + Luhn).

| Corpus | Documents avec détection simulée |
|---|---|
| corpus_ocr, avec libellé | 533 / 600 |
| corpus_ocr, sans libellé | 528 / 600 |
| **corpus_ocr, témoin négatif** | **0 / 400** |
| corpus_flou_realiste | 0 / 400 |
| corpus_courriers | 0 / 400 |
| corpus principal (1 000 documents) | 0 / 1 000 |

Coût mesuré en simulation : **0 masquage à tort sur 2 200 documents sans
identifiant OCR**. Gain : de 0/120 à environ 88 % de documents couverts sans
libellé (528/600 tous types). Pour les types faibles (RPPS, FINESS, SIREN :
Luhn seul), la validité structurelle seule laisse en théorie ≈ 1 chance sur 10
de faux accord pour une suite de 9–11 chiffres contenant une lettre d'OCR ;
le témoin n'en contient aucun, donc le coût réel sur du texte courant avec
suites de lettres O/l/I est **non mesuré au-delà de ce témoin**.

## Incertitudes

- Le témoin (400 documents) est synthétique : il ne prouve pas l'absence de
  faux positifs sur des textes réels (références de dossiers, plaques, codes).
- Le témoin a d'abord contenu un prénom (« OLIVIER ») qui produisait 45 faux
  positifs du détecteur de prénoms, sans rapport avec l'OCR : remplacé par un
  mot neutre ; à ne pas confondre.
- Le prototype n'a pas été exécuté dans `Ecluse.redact` : l'interaction avec
  `resolveOverlaps`, la vue de détection et les avertissements n'est pas mesurée.
- Aucun vrai moteur d'OCR n'est mesuré : les confusions sont injectées au
  hasard, la distribution réelle des erreurs d'un OCR n'est pas connue.
