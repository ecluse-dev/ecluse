# P2-95 — Brancher `ecluse_audit` dans `Ecluse.redact`

Tâche proposée dans `agent/specs/P2-decoupage-fin.md` (bloc C). Document de
conception seulement : aucune ligne de code de production. Il compare des
options et **recommande sans trancher** ; les décisions sont au § 7.

## 1. Ce qui existe (lu dans le dépôt le 2 novembre 2026)

- `ecluse_audit` v0 fabrique et vérifie des entrées chaînées par SHA-256.
  `AuditChain.next` est **sans état** : l'appelant fournit l'entrée précédente,
  l'horodatage (`at`, tronqué à la minute en UTC) et la description du moteur.
  `AuditChain.countsOf(entities)` calcule déjà les comptes par type.
- `AuditSink` n'a qu'une méthode, `append`. `InMemoryAuditSink` sert aux tests.
- Opérations admises : `redact` et `ingestRefused` (énumération fermée, schéma
  version 1). Un refus d'`ingest` porte un code de motif ; un `redact` n'en
  porte jamais.
- Aucun paquet ne l'utilise : `LIMITES.md` le dit « non branché » (le § 8
  décrit le journal lui-même).
- `Ecluse.redact` prend déjà des options facultatives (`riskReference`,
  `dossier`…) et, sans elles, sa sortie est inchangée octet pour octet. Un
  `Dossier` sérialise ses appels (`_serialise`) pour que deux documents
  traités en même temps ne se mélangent pas.
- `DECISIONS.md` : pas d'empreinte du texte ; horodatage à la minute ; la
  bibliothèque ne stocke rien ; `package:crypto` (BSD-3-Clause) approuvé **pour
  `ecluse_audit`** ; aucune trace d'audit pour l'aperçu en v1 (P2-08, n° 5).

## 2. Le problème

Le journal est la preuve qu'un traitement a eu lieu, et de quoi il a masqué.
Aujourd'hui, chaque application doit appeler `AuditChain` elle-même après
`Ecluse.redact`, garder l'entrée précédente, et le faire **dans l'ordre**.
Deux appels concurrents qui lisent la même entrée précédente forkent la
chaîne : `AuditVerifier` signalera alors une rupture qui n'est pas une
falsification. Rien n'empêche non plus d'oublier l'appel.

## 3. Invariants à tenir

1. **Sans journal, rien ne change** : même sortie, même exception, aucune
   écriture (test d'équivalence d'abord, règle 5).
2. **Aucune donnée personnelle** dans une entrée : seuls les comptes par type
   y entrent, comme aujourd'hui (`LIMITES.md` § 8).
3. **Pas d'horloge système dans la bibliothèque** : l'horloge est injectée,
   pour des tests reproductibles (règles de style de `CLAUDE.md`).
4. **Refus explicite** : si l'appelant a demandé un journal et que l'écriture
   échoue, l'appel échoue. Un journal qui saute une entrée en silence est
   pire qu'aucun journal, car il fait croire à une trace complète.
5. **Chaîne linéaire** : une seule entrée suivante par entrée, même sous
   appels concurrents.

## 4. Options

### Option A — Objet `JournalAudit` dans `ecluse_audit`, passé à `redact`

`ecluse_audit` gagne une classe qui tient l'état que `AuditChain` laisse à
l'appelant : sink, entrée précédente, horloge injectée, description du moteur.
Elle sérialise ses écritures (même mécanisme que `Dossier`). `Ecluse.redact`
reçoit un paramètre facultatif `journal` et, après un masquage réussi, appelle
`journal.enregistrer(counts)`.

- Pour : une seule ligne côté application ; l'ordre et la linéarité sont
  garantis par la bibliothèque ; `ingest` pourra utiliser le même objet pour
  ses refus.
- Contre : `ecluse_redact` dépend d'`ecluse_audit`, donc de `package:crypto`
  dans son graphe. La licence est approuvée, mais **pour `ecluse_audit`** :
  l'étendre est une décision.

### Option B — Objet `JournalAudit` seul, sans toucher `redact`

Même classe dans `ecluse_audit`, mais l'application l'appelle après `redact`
avec `AuditChain.countsOf(resultat.entities)`.

- Pour : aucun changement d'`ecluse_redact`, aucune dépendance nouvelle.
- Contre : l'oubli reste possible, et les comptes peuvent diverger de ce qui
  a vraiment été masqué si l'application filtre `entities`.

### Option C — Événement générique émis par `redact`

`Ecluse.redact` accepte un rappel `void Function(Map<String, int> comptes)`
appelé après le masquage, sans connaître `ecluse_audit`.

- Pour : aucune dépendance ; utile à d'autres usages (métriques).
- Contre : la sérialisation et le refus explicite en cas d'échec reviennent à
  l'application ; un rappel synchrone ne peut pas attendre un `append` lent.

### Recommandation (avis, pas décision)

**Option A**, avec une écriture *après* le masquage et *avant* le retour du
résultat : l'application ne peut pas envoyer au LLM un texte dont la trace
n'existe pas. Si la dépendance transitive à `package:crypto` n'est pas
acceptée pour `ecluse_redact`, l'option B livre déjà l'essentiel (ordre et
linéarité) sans toucher au moteur.

## 5. Contrat proposé (esquisse, pas du code)

- `JournalAudit({required AuditSink sink, required DateTime Function() horloge,
  required String moteur, AuditEntry? derniere})`. `derniere` permet de
  reprendre une chaîne existante après redémarrage de l'application.
- `Future<AuditEntry> enregistrerMasquage(Map<String, int> comptes)` et
  `Future<AuditEntry> enregistrerRefus(AuditReason motif)`.
- Écritures sérialisées ; l'entrée n'est considérée comme « dernière » qu'après
  un `append` réussi. Si `append` échoue, l'exception remonte et la chaîne en
  mémoire n'avance pas : un nouvel essai réutilise le même numéro d'ordre.
- Dans `Ecluse.redact` (option A) : paramètre `JournalAudit? journal`. Les
  comptes sont ceux de **toutes** les entités masquées, secrets compris, avant
  restauration éventuelle des secrets (`restoreSecrets`), puisque ce sont les
  détections qui comptent pour la preuve.

## 6. Cas qui demandent une décision

1. **Refus de secrets** (`refuseSecrets`) : aucune opération ne le décrit dans
   le schéma v1. Le journaliser demande une nouvelle valeur d'`AuditOp`, donc
   un schéma v2. Proposition : ne rien journaliser en v1 et le dire dans
   `LIMITES.md`.
2. **Dossier** : un appel dans un `Dossier` produit une entrée comme un appel
   isolé. L'entrée ne porte aucun identifiant de dossier (ce serait une
   donnée de recoupement).
3. **Aperçu** : rien en v1, conformément à P2-08 n° 5 ; seul l'appel final de
   `redact` laisse une trace.

## 7. Décisions pour le mainteneur

1. Option A, B ou C.
2. Accepter `package:crypto` dans le graphe d'`ecluse_redact` (option A
   seulement).
3. Refus de secrets : rien en v1, ou schéma v2.
4. Description du moteur : fournie par l'application, ou construite par
   `ecluse_redact` à partir des détecteurs actifs (dans les 200 caractères et
   la forme admise par `AuditChain`).

## 8. Mesure et tests attendus de la tâche `code`

- Test d'équivalence : sans `journal`, sortie et exceptions identiques sur le
  corpus v3 (graine 42).
- Linéarité : cent appels concurrents donnent une chaîne vérifiée intacte par
  `AuditVerifier`, numéros 0 à 99.
- Échec du sink : l'appel échoue, la chaîne n'avance pas, le nouvel essai
  réutilise le même numéro.
- Contenu : aucune entrée ne contient de sous-chaîne du texte d'entrée (test
  sur le corpus, comme pour `ecluse_audit` v0).
- Coût : l'écriture du journal ne change pas l'ordre de grandeur du temps
  d'un `redact` (mesure par rapport de tailles, pas en temps absolu).

## 9. Ce que cette spec ne sait pas

- Si un journal par appel suffit au besoin d'un DPO, ou s'il faut une entrée
  par session : à confirmer avec l'avis du DPO (P2-97).
- Le coût réel d'un `append` vers un stockage lent chez le client.
